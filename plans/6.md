# Plan for #6: Add PATCH /api/runs/:id/status with allowed transitions

## Goal
Clients can advance a run from `planned` to `running` and from `running` to `done` through a PATCH endpoint.
Creating, listing, reading, and displaying runs remain unchanged.

## Dependencies (confirmed / plausible / open)
- **confirmed, change: yes** — `src/runs.ts` (`RunStatus`, `RunStore`): add body validation and enforce the two domain transitions.
- **confirmed, change: yes** — `src/app.ts` (`createApp`): add the PATCH route, preserve the existing 404 shape, and map invalid transitions to 409.
- **confirmed, change: yes** — `test/app.test.ts` (`runs api`): cover both valid steps, invalid transition, and unknown ID.
- **confirmed, change: yes** — `README.md` API table: document the new endpoint and its 404/409 responses.
- **confirmed, change: no** — `public/index.html`: it renders status but the ticket adds no transition UI.
- **confirmed, change: no** — `e2e/smoke.spec.ts`: existing create/list behavior remains unchanged.
- **confirmed, change: no** — `src/server.ts`: its shared `RunStore` automatically exposes updates.
- **plausible, change: no** — external API consumers may assume immutable status; no consumers exist in this repository.
- **open** — successful response status/body and invalid-body handling require decisions below.

## Tests
- `test/app.test.ts`: PATCH a seeded run through `planned -> running -> done` and assert the updated run.
- `test/app.test.ts`: reject a disallowed transition with 409 and exact `error`, `from`, and `to` fields.
- `test/app.test.ts`: return the existing 404 response for an unknown ID.
- Run `npm run verify`; existing deploy smoke and browser checks should remain green.

## Environment contract
No environment variable is added or changed; `src/config.ts`, `k8s/configmap.yaml`, and the README environment table remain unchanged.

## Risks
- Mutating before validating could leave a run in an invalid state.
- Route-level policy could diverge from store behavior; transition rules will live in `RunStore`.
- Unit/type/build pipeline gates cover the change; rollout, stability, smoke, and browser should be unaffected.

## Open questions
1. Should a successful PATCH return HTTP 200 with the updated run?
2. Should missing, non-string, or unknown `status` values return 400 validation errors, or 409 invalid-transition responses?
3. If the ID is unknown and the body is invalid, should 404 take precedence over body validation?

## Decisions
1. Successful transitions return HTTP 200 with the updated run.
2. Missing, non-string, or unknown statuses return HTTP 400 validation errors with details.
3. Unknown IDs return HTTP 404 before request-body validation.
