# Plan for #5: Enable the metrics endpoint in the deployment

## Goal
Enable the existing plain-text metrics listener in the Kubernetes deployment and document how to access and configure it in the README. The application code and local defaults remain unchanged; this ticket changes deployment wiring and operational documentation.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- **Confirmed — change: yes:** `k8s/configmap.yaml` currently sets `METRICS_ENABLED: "false"`; it must enable metrics and provide the required `METRICS_PORT` read by `src/config.ts`.
- **Confirmed — change: yes:** `k8s/deployment.yaml` exposes only the HTTP container port; add the metrics container port so the deployment declares the listener.
- **Confirmed — change: yes:** `k8s/service.yaml` exposes only HTTP; update it if the metrics endpoint is intended to be reachable through the Kubernetes Service.
- **Confirmed — change: yes:** `README.md` documents the environment variables but not the deployed metrics endpoint or its access path.
- **Confirmed — change: no:** `src/config.ts` already validates `METRICS_ENABLED` and requires a distinct positive `METRICS_PORT`; no new variable is needed.
- **Confirmed — change: no:** `src/server.ts` already starts the metrics listener and serves `sandbox_runs_total` and `sandbox_uptime_seconds`.
- **Confirmed — change: no:** `test/app.test.ts` already covers metrics configuration validation; no application route is added.
- **Plausible — verify during implementation:** `.github/workflows/ci.yml` or smoke checks may assume only the HTTP Service port; inspect before changing, but pipeline edits are out of scope unless required by the deployment wiring.
- **Open — needs a decision:** whether metrics should be exposed by the Kubernetes Service or only declared on the pod for in-cluster scraping.

## Tests
- Update or add deployment-focused manifest assertions if an existing test mechanism is found; otherwise rely on `npm run verify` plus the pipeline rollout/stability/smoke checks.
- Preserve the existing configuration tests in `test/app.test.ts`; add a metrics listener integration test only if the chosen deployment exposure requires application behavior not currently covered.

## Environment contract
`src/config.ts` already defines the contract. The deployment must set `METRICS_ENABLED=true` and `METRICS_PORT` to a positive port different from HTTP `3000`; `k8s/configmap.yaml` and the README environment table/documentation must remain synchronized. No new application environment variable is introduced.

## Risks
- A missing or conflicting `METRICS_PORT` causes startup failure and deployment rollout failure.
- Declaring the wrong target port or Service port makes metrics unreachable even though the pod is healthy.
- Exposing metrics publicly through the wrong Service path could broaden access beyond the intended in-cluster monitoring scope.
- Pipeline failure points include deployment rollout, pod stability/restarts, smoke checks, and any browser check indirectly affected by a failed rollout.

## Open questions
1. Should the metrics port be exposed through the `sandbox-app` Kubernetes Service, or should it remain pod-only for an in-cluster scraper?

## Decisions
- Metrics will be exposed through the `sandbox-app` Kubernetes Service.
